# SIMD open-addressing lookup benchmark

Google Benchmark comparison of four insert-only hash-table lookup kernels:

| Benchmark | Storage | Home and probing |
| --- | --- | --- |
| `ScalarOA` | Adjacent 8-byte key/value pairs | Exact home cell, then consecutive cells |
| `ScalarGroupedOA` | Four keys followed by four values in each 64-byte group | Home cache line, then consecutive groups; scalar comparisons |
| `ScalarCyclicGroupedOA` | Same 64-byte layout | Hash-selected starting lane, cyclic scalar scan within each group |
| `SIMDGroupedOA` | Same storage and insertion as `ScalarGroupedOA` | Same group probing; xsimd comparisons |

The grouped scalar control separates SIMD's contribution from the change in
layout and probing. All table allocations start on a 64-byte boundary. The SIMD
kernel uses explicit NEON64 or AVX2 batches, covering exactly four 64-bit keys.
All SIMD intrinsics stay inside xsimd.

See [RESULTS.md](RESULTS.md) for the measured ARM comparison through `2^28` keys.

Hashing XORs the two 32-bit halves of a key, then applies MurmurHash3's `fmix32`
finalizer. Equality uses the complete 64-bit key. Key zero marks empty cells;
inserting it throws, and looking it up returns no match. Values may be zero.
Inserting an existing key updates its value. There is no deletion or resizing.

Capacity is `max(4, 2 * bit_ceil(distinct_keys))` cells. New insertions stop at
half the capacity, and duplicate updates remain allowed. The benchmark uses
power-of-two key counts, giving exactly 0.5 load. Non-power-of-two requests have
lower realized load. A group starts at `(hash & (capacity - 1)) >> 2` and wraps
at the end of the table. The original grouped lookups check for matches before
stopping on an empty group lane.

The cyclic scalar experiment uses `hash & 3` as its starting lane for both
insertion and lookup. Every group is scanned in order `(start + offset) & 3`,
with offsets zero through three. The same starting lane is retained after
advancing to another group. Lookup returns on a match or the first empty lane
in that order. This is safe because insertion fills the first empty lane in
the same order, and entries are never deleted or moved. Cyclic insertion does
not preserve a physical occupied prefix, so testing only the final lane for
emptiness would be incorrect.

## Build and check

Requires Clang with C++20, clang-format, clang-tidy, Meson, Ninja, and CMake.
Clang and its tools were validated at version 22.1.8. Dependency archives are
pinned and verified by the Meson wraps; initial setup needs network access
unless the archives are already cached in `subprojects/packagecache`.

```sh
CXX=clang++-22 meson setup build --buildtype=release
meson compile -C build
meson test -C build --print-errorlogs
meson compile -C build format-check tidy
```

Use your installed Clang executable if it has a different name. Meson selects
NEON64 on AArch64 and AVX2 on x86-64. The x86 binary requires an AVX2-capable CPU.
Automatic loop and SLP vectorization are disabled for project code so the scalar
controls remain scalar; explicit xsimd operations still generate vector code.

The root `.clang-format` and `.clang-tidy` are copies of the ClickHouse root
configurations. `meson compile -C build format` formats only project C++ files.

```sh
CXX=clang++-22 meson setup build-sanitize --buildtype=debug \
    -Db_sanitize=address,undefined
meson compile -C build-sanitize
meson test -C build-sanitize --print-errorlogs
```

## Measure

The default matrix covers `2^10, 2^12, ..., 2^28` distinct keys and 0%, 50%, and
100% hits. Use Google Benchmark's filter to select a smaller run. List the exact
names with `build/oa_bench --benchmark_list_tests`.

A quick run uses `--benchmark_filter='.*keys:1024/' --benchmark_min_time=0.02s`.
To run only the largest tables, use `--benchmark_filter='.*keys:268435456/'`.

```sh
mkdir -p results
taskset -c 8 build/oa_bench \
    --benchmark_min_time=0.2s \
    --benchmark_min_warmup_time=0.1 \
    --benchmark_repetitions=3 \
    --benchmark_enable_random_interleaving=true \
    --benchmark_out=results/lookup.json \
    --benchmark_out_format=json
```

Choose an idle CPU allowed by your environment. Allocation, insertion, query
generation, and shuffling are outside timing. Each variant receives identical
keys, insertion order, values, and shuffled queries. Keys are generated by a
bijective 64-bit permutation; misses come from a disjoint input range. A full
query trace contains as many keys as the table contains distinct keys, avoiding
a small repeatedly accessed subset of a large table.

Each timed batch probes the full trace and consumes returned values and hit
counts. Google Benchmark counts logical lookups with `KeepRunningBatch`, so its
reported nanoseconds and items/second are per lookup. Aggregate hit counts and
value checksums are verified after timing. Measurements include hashing and
value loads. Independent queries measure throughput, not serialized lookup
latency. There is no explicit prefetching or multithreading.

At `2^28` keys the table occupies **8 GiB**, with **2 GiB** for the query trace.
Construction generates keys on demand, and variants run sequentially. Repeated
runs still rebuild large tables, so a complete matrix can take substantial time.
Report both the table and query footprints when interpreting cache effects.

Correctness tests compare both layouts and all lookup paths with a bounded
reference map. They cover collisions, full groups, wraparound, high key bits,
duplicate updates, sizing limits, and empty tables. Large benchmark runs use the
known workload hit counts and checksums instead of allocating a second large
reference table.
